# Безопасность SRTube

Проверка и изменения: 4–5 ноября 2026. Это разбор конкретных границ доверия, а не гарантия отсутствия всех уязвимостей.

## Что считается недоверенным

Ссылки, параметры, callback, заголовки YouTube, аудио и обложки. Даже результат обработчика медиа проверяется перед отправкой. Код из pull request выполняется только на GitHub-hosted runners. Dev-код не является установленным production-контроллером.

## Приложение

| Риск | Защита |
| --- | --- |
| SQL-инъекция | Параметризованные запросы SQLite, проверка ID, отсутствие пользовательского SQL. Регрессионный тест с SQL-payload. |
| Командная инъекция | Аргументы subprocess без shell; параметры звука числовые; shell-подстановки остаются буквальным аргументом. |
| SSRF | Только канонические YouTube video URL. Обложки только с фиксированного `i.ytimg.com`, без redirect. FFmpeg без сети и сетевых протоколов. |
| Чтение произвольных файлов | ID/имена файлов ограничены; симлинки отклоняются. Перед отправкой файл открывается через `O_NOFOLLOW` и `dir_fd`, проверяется `fstat`, копируется в закрытую папку бота. |
| Утечка учётных данных | Дочерние процессы не наследуют BOT_TOKEN/GITHUB_TOKEN; cookies и metadata находятся вне общей папки обработчика; токен production хранится файлом в отдельном томе. |
| Доступ через чужие кнопки | Авторизация по числовому Telegram ID и владельцу трека, повторная проверка перед обработкой и отправкой. `/id` показывает только собственный ID. |
| DoS / заполнение диска | Очередь, одна задача на пользователя и один worker, ограничение частоты, timeout, лимиты stdout/stderr, kernel `RLIMIT_FSIZE`, проверка свободного места, ограниченный кэш. |
| Опасные декодеры | Pillow обновлена до 13, открывает только JPEG с ограничением пикселей. FFmpeg собирается только с необходимыми аудиодекодерами/форматами/фильтрами. |
| Сбой subprocess | Останавливается вся группа, включая потомков; pipes дренируются после остановки, чтобы не зависнуть на переполненном выводе. |

## Контейнеры production

Бот имеет только исходящую сеть, закрытый том state и том tracks. Обработчик имеет только tracks и Unix socket, **без сети, токена, базы и cookies**. Исходники, `/usr`, библиотеки и корневая файловая система доступны только для чтения. Ни Docker socket, ни домашняя папка Mac, ни SSH-ключи в контейнеры не подключаются. Убраны capabilities, запрещено повышение привилегий, заданы лимиты PID/RAM/CPU, временные папки — tmpfs с `noexec`/`nosuid`.

Для 1 CPU / 2 ГБ RAM:

- bot: максимум 0,25 CPU и 512 МБ RAM;
- renderer: максимум 0,55 CPU и 512 МБ RAM;
- опциональный PO Token provider: максимум 0,10 CPU и 256 МБ RAM;
- одна тяжёлая задача одновременно, FFmpeg с одним потоком, кэш 1 ГБ, резерв диска 512 МБ.

Лимиты ограничивают потребление, но не гарантируют скорость на любом CPU. Сборка и сканирование происходят в CI, не на VPS. Mac использует нативный ARM64-образ, будущий Intel VPS — AMD64.

Локальная проверка финального ARM64-образа: 120 секунд синтетического аудио → оригинальный MP3 с ID3/обложкой, slowed + reverb и Opus-превью заняли 4,72 с при лимите 0,55 CPU; пиковая RSS дочернего процесса — около 83 МиБ. Это проверка DSP на Mac, без скачивания YouTube и отправки в Telegram; скорость на VPS измеряется отдельно. Воспроизвести проверку можно командой `python -m srtube.selftest --seconds 120` внутри образа.

## YouTube-аккаунт

Используй отдельный аккаунт без личной почты, платёжных данных и приватных видео. Включи двухфакторную защиту. Пароль не хранится в SRTube. Сохраняются только cookies YouTube, а cookies Google и других сайтов отбрасываются. Бот отклоняет приватные материалы и материалы с доступом по подписке аккаунта.

**Cookie — действующая сессия.** Тот, кто получит её, может использовать её без нового ввода пароля/2FA. Права `600`, отдельный том и изоляция обработчика сокращают доступ, но не защищают от администратора Docker/ОС или полного взлома downloader. При утечке отзови сессию в Google и импортируй новую. Не используй основной личный Google-аккаунт.

## Поставка и обновление

CI выполняет lint, тесты, Bandit, pip-audit, проверку секретов и Gitleaks. Оба образа (AMD64/ARM64) проходят реальную офлайн-проверку MP3/ID3/обложки/Opus и Grype. High/Critical останавливают публикацию. Actions, исходные образы, tarball FFmpeg и ключ подписи зафиксированы; tarball дополнительно проверяется подписью FFmpeg с известным fingerprint.

Runtime построен на закреплённом Wolfi base с актуальными пакетами Python 3.12 / Node 24. Установщик uv остаётся только на этапе сборки. Экспериментальный PO Token provider не входит в проверенный production-релиз: его override требует отдельный прошедший аудит digest, известный старый сторонний образ автоматически не запускается.

### SQLite CLI: неприменимое предупреждение сканера

Grype сопоставляет `CVE-2026-119586` с пакетом `sqlite-libs 3.54.1-r0`. [Исходное исследование](https://abraxaslabs.tech/research/sqlite-cli-recover) описывает инъекцию в выводе `.recover` командной оболочки SQLite при последующем исполнении этого вывода второй оболочкой; библиотека `libsqlite3` не затронута этим сценарием. В образе установлена только библиотека: `sqlite3` executable и символ `sqlite3_recover_init` отсутствуют. Backup выполняется через Python `Connection.backup`, без `.recover` и shell pipe.

В `.grype.yaml` указано единственное исключение для этого CVE, имени и точной версии APK. На каждой архитектуре CI отдельно проверяет отсутствие CLI и recovery API перед сканированием. Если компонент появится, CI остановится и исключение нужно пересмотреть. Другие High/Critical, включая уязвимости SQLite, продолжают блокировать выпуск. Оставшийся `CVE-2026-103995` имеет Low severity и виден в отчёте; известные уязвимости не объявляются полностью отсутствующими.

Production-контроллер выбирает успешный CI для **текущего HEAD main**, скачивает его маленький release-артефакт и использует точный digest. Mutable `latest`/`main` не используются. Контроллер установлен вне dev checkout и выполняется изолированным системным Python, без входящих портов и без self-hosted runner. Новая версия заменяет старую только после проверки здоровья; неудачная выкладка восстанавливает прежний образ и блокирует повтор того же коммита. База перед обновлением копируется штатным SQLite backup; автоматического отката базы нет, чтобы не восстановить отозванные права пользователей.

Текущий приватный репозиторий на GitHub Free не поддерживает обязательную защиту `main` (API вернул HTTP 403). Репозиторий остаётся приватным. CI/CD не применяет неуспешный коммит, но запретить push владельца средствами приложения нельзя. Для серверного запрета прямого push нужен подходящий тариф GitHub. Работай через PR и проверяй изменения `.github/`, `ops/`, Dockerfile и зависимостей.

## Остаточные риски и обслуживание

- Компрометация владельца GitHub, Mac/ОС, Docker daemon или production downloader остаётся серьёзным инцидентом. Контейнер не является абсолютной границей против уязвимости ядра.
- Скомпрометированный renderer сможет читать/повреждать общий кэш аудио. Он не должен иметь доступа к state; тесты проверяют mount/network boundary и защиту отправки от симлинков.
- Проверки зависимостей находят известные advisories, не доказывают отсутствие неизвестных. Обновляй ОС, Docker Desktop и базовые образы; проверяй обновления FFmpeg и Pillow. Dependabot готовит изменения зависимостей/Actions/Docker, но исходный FFmpeg нужно обновлять с проверкой подписи/хэша.
- YouTube может ограничить IP/сессию, а Telegram — быть недоступен. Healthcheck и откат не отменяют внешние ограничения.
- На VPS не используй root для постоянной работы приложения. Предпочтителен отдельный пользователь и Docker rootless с cgroup v2; проверь фактическое применение лимитов. Перенос на VPS и SSH-настройки выполняются отдельно.
- Бэкапы базы находятся в state и не переживут потерю всего диска. Для VPS потребуется отдельная зашифрованная внешняя копия. Бэкапы приложения не содержат cookies и bot token.
